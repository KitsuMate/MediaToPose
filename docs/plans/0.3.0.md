# Media to Pose 0.3.0: fast SAM 3D Body, Kimodo text to motion, agentic command line

Branch: `feature/0.3.0`, cut from `main` at the 0.2.1 merge (`dab26d5`).

## Why

**SAM 3D Body is too slow to use on video.** A frame with hands takes about
5.8 s on WebGPU (RTX 3070 Laptop, `vith-candidate-v3/webgpu-parity.json`),
and loading the model takes over 17 s. The causes are mostly in our runtime,
not in the network:

- A frame with hands makes 100 `session.run` calls across 22 sessions
  (`backends/sam3d/vith/runner.py`). It runs the backbone three times: body,
  then left and right hand separately, although batch 2 costs 0.76 s against
  0.58 s for batch 1.
- There is no IO binding. Image tokens, positional encodings and features
  (about 3.9 MB each per person) are uploaded again for every decoder layer
  and keypoint updater, about 290 MB host to device per person per frame.
- The fp16 backbone output is downloaded, cast to fp32 on the host and
  uploaded again. Every decoder, head and updater graph is fp32.
- Each frame runs 26 NumPy MHR forwards over the full 18,439-vertex mesh.
  Each forward includes a 4.5M-nnz corrective MLP, an `np.add.at` LBS, a
  zero face einsum and a Python loop over 127 joints. Yet the decoder loop
  only needs 70 keypoints, which `keypoint_mapping.bin` builds from about
  545 vertex and joint entries.
- No `SessionOptions` are set. WebGPU graph capture is off, and Gather,
  Concat and Slice nodes inside the WebGPU graphs fall back to the CPU (606
  of 3,912 backbone nodes).
- Every model load re-hashes 1.76 GB. Video decode, MediaPipe and SAM all
  run in series on one thread.
- The export and parity scripts behind the published bundle are not in the
  repository or in `.workspace/`, so no new variant can be built or checked
  reproducibly.

**Animators want to block a shot with a few poses and fill in the rest.**
NVIDIA Kimodo (SOMA, Rigplay v1.1) is already converted to ONNX, together
with its LLM2Vec text encoder. It generates motion from text and takes
full-body, hand/foot and root-path constraints, which match keys an
animator has already set. The complete integration plan is
`docs/plans/0.3.0-kimodo.md`.

**Agents can drive capture but not these features.** The command line
(`api/cli.py`) cannot install models, cannot plan a run before paying for
it, and starts a new Blender process for every command. With a 5.8 GB
encoder and 17 s of SAM session setup, each extra process is expensive.
Results also cannot be replayed with one setting changed.

## Goals

1. **Faster SAM 3D.** On the reference laptop with WebGPU, a frame with
   hands in at most 1.5 s and a body-only frame in at most 0.6 s. On CPU, at
   least 2× faster than today. A warm model reload in at most 5 s. Results
   stay within the published parity tolerances. Phase A0 confirms or
   adjusts these targets from measured baselines before work starts.
2. **New SAM 3D variants.** Faster variants published under
   `onnx/vith-<suffix>/` in `KitsuMate/sam-3d-body-onnx`, each with a
   manifest, provenance, CPU and WebGPU parity reports and a benchmark
   report. The add-on picks a variant by device.
3. **Text to motion and in-betweening on any mapped humanoid rig.**
   Existing keys guide the result and stay untouched; prompts are optional.
   Goals, scope and done-when are in `docs/plans/0.3.0-kimodo.md`.
4. **Every new feature is complete on the command line.**
   - Models can be installed with an explicit licence acceptance.
   - Every run can be planned first (`--dry-run`), replayed from its result
     (`--recipe`), and batched in one Blender process.
   - Progress is machine-readable.

Out of scope:

- the DINOv3 SAM variant, multi-person capture, and CUDA or TensorRT
  wheels;
- Kimodo as a capture clean-up module, and changes to RoHM
  (`docs/plans/learned-correction.md`, a later version);
- the Kimodo exclusions listed in `docs/plans/0.3.0-kimodo.md`.

## Track A: SAM 3D speed

### A0. Measure first

- `ci/sam3d/bench.py`:
  - Runs the installed bundle on the parity golden
    (`vith-golden/ref_pose_full.npz`) and on a 60-frame clip from
    `tests/fixtures/`.
  - Covers WebGPU and CPU, body-only and with hands.
  - Reports wall time per stage: decode, MediaPipe, crop, backbone, each
    branch, MHR, conversion. Also reports session creation, load time and
    peak RSS.
  - Writes `bench_report.json`.
- Per-stage timing inside the runtime goes to `LOGGER.debug`, with a
  `timings` field on the provider's per-frame diagnostics. It has no cost
  when debug logging is off.
- `ci/sam3d/parity.py`: re-creates the missing parity harness.
  - Compares any bundle folder against the golden with the tolerance table
    in `onnx/vith/parity_report.json`.
  - WebGPU keeps the reviewed `pred_keypoints_2d` override of 16 px.
  - Writes `parity_report.json` in the published schema.
- The end-to-end gate is unchanged:
  - the pose thresholds in `ci/provider_integration_blender.py`;
  - the VRoid e2e test against `sam_ref_pose_stylized.json`.
- Record the baselines in the plan's Outcome section, then fix the numeric
  targets in Goal 1.

### A1. Runtime fixes, no new weights

Ordered by expected gain. Measure each change with `bench.py` and commit
only measured wins.

1. **Batch the hands.**
   - Run the left and right hand through one backbone call and one branch
     pass at batch 2N.
   - Skip the hand path entirely when hands are not requested.
   - Batch outputs were bit-identical in `branch-batch-validation.json`.
2. **Slim MHR inside the decoder loop.**
   - A `decode_keypoints` path computes only what the 70 keypoints and the
     camera projection need:
     - corrective rows for the vertices referenced by
       `keypoint_mapping.bin`;
     - LBS over those vertices only;
     - no face einsum while face coefficients are zero.
   - The full mesh forward runs once per frame, for the final output.
   - Vectorise the 127-joint loop by depth level. Replace `np.add.at` with
     `np.bincount` or a dense gather.
   - Equivalence test against the full forward on recorded parameters.
3. **Load fast.**
   - Hash at install and store a size and mtime stamp. Load checks the
     stamp; `verify` still hashes everything.
   - Pin `manifest.json` by SHA-256 in `MODEL_VARIANTS`.
   - Remove the fallback to `main` for pinned revisions.
   - Enforce `model_revision` at install, not only at load.
4. **Session options.**
   - `graph_optimization_level = ORT_ENABLE_ALL` and explicit intra-op
     threads on CPU.
   - Fetch only the outputs that are used (drop `hand_logits`).
   - Check whether WebGPU graph capture can be enabled once A2 removes the
     CPU fallback nodes.
5. **Keep tensors on the device.**
   - Spike: use IO binding with WebGPU `OrtValue`s so that `image_tokens`,
     `image_pe` and `features` stay on the GPU between sessions.
   - If ORT 1.27's Python binding cannot share WebGPU buffers across
     sessions, skip this. The fused variant in A2 removes the crossings
     anyway.
6. **Crops.**
   - Warp straight into the 512×384 trimmed window.
   - Cache the ray-condition grid per shape.
   - Crop the left hand with a flipped affine transform instead of copying
     the whole flipped frame.
   - Convert colour once.
7. **Pipeline the video.**
   - A producer thread decodes frame n+1 and runs the MediaPipe locator
     while SAM runs on frame n. It uses a bounded queue of `core` types and
     honours the cancel event.
8. **Warm start (experiment).**
   - Feed the previous frame's estimate (`prev_estimate`,
     `use_initial_estimate=False`) and try fewer decoder iterations.
   - It changes results, so it ships only behind a setting, and only if
     `evaluate` jitter and the e2e thresholds do not get worse.

The runner reads input dtypes from `session.get_inputs()` instead of
hard-coding fp16 and fp32 (`vith/crops.py:112-116`, `vith/runner.py:78-87`),
so any precision mix in a manifest works without code changes.

### A2. New variants (offline, `ci/sam3d/export/`)

Every variant starts from the published fp32 and fp16 graphs and the MHR
artifacts, so it needs no PyTorch checkpoint. Graph changes use `onnx`,
`onnxconverter-common`, `onnxruntime.quantization` and a small PyTorch module
for MHR keypoints, run in a `.workspace` venv. Candidates, in order:

| Folder | Contract | Change | Expected win |
|---|---|---|---|
| `onnx/vith-fp16` | `sam3d.raw.v1` (same 22 roles) | Decoders, heads and updaters in fp16. LayerNorm, Softmax, ReduceMean and Pow are kept in fp32 (`op_block_list`). Constants are folded so no Gather, Slice or Concat falls back to the CPU. | Half the upload size, faster GPU matmuls, no host-side cast |
| `onnx/vith-fused-fp16` | new `sam3d.fused.v1` | 3 graphs: `backbone` (normalisation and trim folded in), `branch.body` and `branch.hand`. Each branch graph is the token initializer plus 6 × (layer, norm, raw head, MHR keypoints, camera projection, updater) as one graph. `hand_box_head` folds into the body branch. | 100 runs per frame drop to about 6, with no host round trips inside a branch |
| `onnx/vith-q8` | `sam3d.raw.v1` or `fused.v1` | Weight-only int8 (MatMulNBits or QDQ) on the backbone and decoders, for CPU. | CPU speed and a smaller download |

- **MHR keypoints in ONNX.** The fused graph needs the slim keypoint path
  from A1.2 written as a PyTorch module. That covers the 6D-to-matrix
  conversion, the parameter transform, the corrective rows, the FK chain
  over 127 joints, LBS over the mapped vertices, the keypoint mapping and
  the camera projection. It is exported with fixed tensors from the MHR
  artifacts, and A1.2's NumPy path is its reference. The final full-mesh
  pass stays in NumPy.
- **Gate for each candidate:**
  - CPU parity within the release tolerances;
  - WebGPU parity within the reviewed tolerances;
  - 100 % of nodes on WebGPU for fp16 variants;
  - the e2e pose thresholds;
  - at least 20 % faster than the best earlier variant on its target
    device.
  A candidate that fails the gate is recorded in Outcome and not published.
- **Published folder layout:** each folder holds `manifest.json`,
  `PROVENANCE.json` (sources plus the export script commit),
  `parity_report.json`, `parity_report.webgpu.json` and `bench_report.json`.
  The MHR artifacts are duplicated per folder so the existing downloader
  works. Re-using them across folders would save about 82 MB and is not
  worth a schema change now.

### A3. Publish and integrate

- **Upload** each approved folder:
  `hf upload KitsuMate/sam-3d-body-onnx <dir> onnx/vith-<suffix>`. Then
  update the README variant table in a second commit.
- **Record the resulting Hugging Face commit** in `MODEL_VARIANTS`
  (`backends/sam3d/backend.py:54-67`), together with the manifest SHA-256
  and the download size. Each entry is one variant: `VITH`, `VITH_FP16`,
  `VITH_FUSED_FP16`, `VITH_Q8`.
- **Runtime:** `vith/` gains a fused runner beside the split runner, chosen
  by the manifest `contract`. `graphs.py` validates the role set per
  contract.
- **Variant choice:**
  - `sam3d_model_variant` gets an `AUTO` default: the fused fp16 variant
    when the selected device is WebGPU or CoreML, and q8 (or fp32) on CPU.
  - The install dialog shows the size of each variant.
  - Only one variant is installed at a time, as today. Switching downloads
    the new variant and keeps `.previous` until it verifies.
- **Cache:** the detection cache fingerprint (`providers/sam3d/state.py`)
  includes the variant, so cached detections from another variant are not
  reused silently.
- **Docs:** the speed table and variant choice go in the README and
  `docs/agents.md`. `api.model_status` reports the variant and the device.

## Agentic command line

Rules for every 0.3 feature:

- **API first.** Every feature is an `api` function first; the CLI is a thin
  wrapper. `tests/unit/test_agent_docs.py` keeps the docs complete.
- **Output discipline.** With `--json`, stdout carries exactly one JSON
  document. Logs go to stderr.
- **Data safety.** Blender data changes only inside a transaction. Nothing
  is saved without `--save`.

### New and changed commands

| Command | API | Notes |
|---|---|---|
| `models` (no subcommand) | `api.model_status` | Unchanged output, plus variant, device and licence state |
| `models install NAME [--variant V] [--accept-license ID]` | `api.install_model` | NAME is `sam3d`, `rohm`, `anycalib`, `kimodo` or `llm2vec`. Blocks with progress; resumes partial downloads |
| `models load\|unload\|verify\|uninstall NAME` | `api.load_model`, … | `verify` re-hashes; `load` warms a model inside `batch` |
| `models benchmark sam3d [--media M] [--frames N]` | `api.benchmark_model` | Writes the A0 `bench_report.json` fields, so agents can choose a variant |
| `guides --armature A [--frame-range F:L]` | `api.describe_guides` | Frames, guide kind and joints, plus warnings (too dense, collisions) |
| `generate --armature A [--prompt P \| --segment F:L:P ... \| --markers] [--frame-range F:L] [--path CURVE] [--seed N] [--steps N] [--text-guidance W] [--guide-guidance W] [--no-guides] [--candidates N --keep best\|all] [--key-spacing N] [--interpolation LINEAR\|BEZIER] [--output ...] [--device ...]` | `api.generate` | `--keep all` puts every candidate on its own NLA track, as the foot-contact recipe does today |
| `keep-candidate --armature A --result FILE --seed N [--output ...]` | `api.keep_candidate` | Bakes one candidate track into the action and removes the others |
| `capture` / `retarget` | unchanged | Results gain `inference_seconds`, `seconds_per_frame`, `model_variant` and `device` |
| `keys list\|clear --armature A --frame-range F:L [--parts body,hands]` | `api.list_keys`, `api.clear_keys` | Clearing a range before regenerating it ("replace a section"); creating poses stays with Python or MCP |
| `encode-prompt P` | `api.encode_prompt` | Fills the embedding cache, so later runs never load the encoder |
| `batch FILE\|-` | `api.run_batch` | See below |
| `schema [capture\|generate\|evaluate\|error]` | `api.result_schema` | JSON Schema of each document, built from the dataclasses |

`generate`, `capture` and `retarget` all accept:

- **`--dry-run`.** Resolve settings, read guides, plan the windows,
  check mapping, models, licences, RAM and disk, and estimate seconds (from
  the last benchmark, or defaults). Return a `Plan` document without
  loading a model or changing Blender data. An agent learns "needs the
  5.8 GB encoder, 3 windows, about 40 s" before paying for it.
- **`--recipe RESULT.json`.** Every result carries a `recipe`: all resolved
  settings, seed, model variant, revisions and guide set. Passing it back
  re-runs the same work, and explicit flags override single fields. The
  same recipe and seed give bit-identical keys on the same device and
  variant; a test enforces this.
- **`--progress jsonl`.** One JSON line per progress update on stderr, with
  `phase`, `done`, `total`, `eta_seconds`, plus download bytes for
  installs.
- **`--timeout S`.** SIGINT is also handled, so cancellation rolls back as
  `CANCELLED`.

### One process, many steps: `batch`

Each new process pays for Blender startup, SAM sessions (about 17 s today)
or the text encoder (5.8 GB). `batch` reads JSON lines:

```
{"command": "models", "args": ["load", "kimodo"]}
{"command": "generate", "args": ["--armature", "Rig", "--prompt", "walks and waves", "--seed", "3"]}
{"command": "evaluate", "args": ["--armature", "Rig"]}
```

It runs them in order in one process and prints one JSON result per line.

- It stops at the first error unless `--keep-going` is given.
- `--save` saves once, at the end.
- Loaded models and the prompt cache stay warm between steps.

Interactive agents can still use the Python API through the Blender MCP
server, which keeps models loaded in the open session; `docs/agents.md`
says when to use which. A long-lived server process is out of scope.

### Errors and licences for agents

New error classes, each with a stable code and exit code:

| Exit | Code | When |
|---|---|---|
| 10 | `LICENSE_REQUIRED` | A model's licence has not been accepted. `details` carries the licence id, a summary, the URL and the exact `--accept-license` value |
| 11 | `INSUFFICIENT_RESOURCES` | Not enough disk or RAM. `details` gives needed and available bytes, and which variant would fit |
| 4 | `ONLINE_ACCESS_DISABLED` (a `ModelMissing` subclass) | Blender's online access is off; nothing is downloaded |

`docs/agents.md` states the rule for agents: on `LICENSE_REQUIRED`, show the
licence to the user and pass `--accept-license` only after the user agrees.
An agent never accepts on its own. The acceptance is recorded with who
accepted it (CLI or panel) and when.

### Metrics for generated motion

Given a generate result, `evaluate` gains `guide_error_m`,
`guide_warp_deg`, `seam_jump_deg` and `regenerated_frames`, as specified in
K7 of the Kimodo plan. Each gets a "good / investigate / what to change" row
in `docs/agents.md`, next to the Kimodo recipes.

## Order and parallel work

Track A, Track B (the Kimodo plan) and the shared command line parts touch
different files, so they can run in parallel sessions.

1. **Shared foundations first,** each as its own commit:
   - the `install_pinned_bundle` changes (disk, resume, online access) and
     `backends/resources.py`;
   - the new error classes;
   - `--progress jsonl`, `--dry-run` and `Plan`;
   - `recipe`, `batch` and `models install`.

   They are useful for capture right away.
2. **Track A:** A0 → A1 → A2 → A3. Uploads happen inside A3, one approval
   per folder.
3. **Track B:** in the order given in the Kimodo plan. Each feature adds
   its command in the same commit as its API.
4. **Release:** tests grow with each phase. Visual review, version bump to
   0.3.0, CHANGELOG and PR text come last. Ask before pushing and before
   opening the PR.
